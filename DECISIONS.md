# Decisions

A running log of non-obvious architectural, infra, and tradeoff decisions for this project — the "why," not the "what" (the code and `SYSTEM_DESIGN.md` cover that). Started 2026-09-04, going forward; not a complete history of everything ever decided. Newest entries at the bottom.

Entry shape: date, the decision, alternatives considered, why.

---

## 2026-09-04 — Hold music plays via Asterisk's `mode=mp3` (mpg123), not `mode=files`

**Decision**: The `[custom]` MOH class in `musiconhold.conf` uses `mode=mp3` (shells out to `mpg123` to decode on the fly), and `mpg123` was installed on the VPS for this.

**Alternatives considered**: `mode=files` pointing at the uploaded raw MP3 — simpler config, no new system package.

**Why**: This box's Asterisk build has no native MP3 format module, and `mode=files` only plays formats Asterisk can decode itself (wav/gsm/sln/ulaw/ogg). Confirmed live: with `mode=files`, Asterisk silently never even registered the class — no error, the class just didn't show up in `moh show classes`. `sox` (already used elsewhere in this app for Piper TTS) also has no MP3 support built into this box's copy, ruling out a transcode-at-upload-time approach without also adding a codec library. `mode=mp3` was the smallest fix: one small, standard system package, zero changes to the upload code (still stores/serves plain MP3 as uploaded).

## 2026-09-04 — DigitalOcean auto-deploy needed manual reconnection after the GitHub repo rename

**Decision**: No code change — flagged that `calls-app`'s DigitalOcean App Platform source was still pointing at the old GitHub repo name (`at-voice-app`) after the repo was renamed to `calls-app`, and had the user reconnect it via the DO dashboard (Settings → source).

**Alternatives considered**: Trigger a deploy manually via `doctl apps create-deployment` — attempted, but the API token in use doesn't have permission for that action, so it wasn't a real option here regardless.

**Why**: A push to `main` stopped triggering deploys with no error surfaced anywhere obvious — DO's GitHub webhook/App-installation link doesn't automatically follow a repo rename. Worth remembering if deploys silently stop working again after any future repo-level change (rename, transfer, etc.) — check the DO app's source connection first, not the code.

## 2026-09-04 — Orphaned add-party requests get swept by age, not tracked in memory

**Decision**: Added `call_logs.add_party_updated_at` and a periodic sweep (`sweepStaleAddPartyRequests`, `ari-app/supabase.js`) that fails any row stuck at `add_party_status='dialing'` for more than 2 minutes — same shape as the existing `sweepStaleCalls`.

**Alternatives considered**: An in-memory `Set` of session ids this process has actually claimed, checked against `add_party_status='dialing'` rows on a sweep — rejected because it's more bookkeeping (add/remove across multiple call sites) for no real benefit: an age-based DB sweep also correctly handles the same orphan surviving a process restart (in-memory state doesn't survive that either way), and it matches a pattern already used elsewhere in this file, which a future maintainer will recognize on sight.

**Why**: Found via log analysis (see the week's log audit) — `claimAddPartyRequests`'s claiming `UPDATE ... RETURNING` can commit on Supabase's side while the HTTP response is lost to a timeout or transient `Bad Gateway` (confirmed: 5 occurrences in under a week of production logs). When that happens, this process never learns the session id, so none of the *other* already-existing recovery paths for a stuck add-party request (both in `bridgeAddPartyDest`/`completeAddParty`, `ari-app/index.js`) ever run — they only cover legs this process actually originated. Without this sweep, the dashboard would show "Adding party…" for that call forever.

## 2026-09-04 — `calls-app` now sets `trust proxy` for DigitalOcean's edge proxy

**Decision**: `app.set('trust proxy', 1)` added to `calls-app/app.js`.

**Alternatives considered**: None seriously — this is the standard, documented fix for an Express app behind exactly one reverse proxy.

**Why**: Found via log analysis — every rate-limited request was logging an `express-rate-limit` validation error (`ERR_ERL_UNEXPECTED_X_FORWARDED_FOR`) because Express didn't know to trust DigitalOcean App Platform's `X-Forwarded-For` header. Confirmed this wasn't actually breaking requests (still got correct responses), but it meant the rate limiter likely wasn't identifying real client IPs correctly, and the resulting log noise was making genuine errors harder to spot — directly slowed down this same log audit.

## 2026-09-04 — Startup reconciliation now checks real Asterisk channel state before marking a call "failed"

**Decision**: `reconcileStaleCallsOnStartup` (`ari-app/supabase.js`) now takes a `Set` of currently-live Asterisk channel ids (from `client.channels.list()`, gathered in `index.js`'s `main()` right before calling it) and only marks a non-terminal `call_logs` row `'failed'` if its channel is actually gone. A row whose channel is still live and pre-bridge (never reached an agent) gets actively hung up instead (`client.channels.hangup()`) rather than left to sit forever; a row still live and already `'ongoing'` (a real bridged conversation) is left completely alone. `markMissedIfAbandoned` (run from the global `StasisEnd` handler for every channel that ends) was widened to also close out a still-`'ongoing'` row as `'completed'` once it actually ends, since an orphaned one no longer has a `teardown()` closure left to do that itself.

**Alternatives considered**: Leaving the blind "mark everything failed" behavior and instead trying to have `sweepStaleCalls`'s existing age-based cutoff catch these sooner — rejected because the actual bug isn't the row being wrong for a while, it's that a genuinely still-connected caller (sitting in the hold queue, hearing hold music) has nothing left in the new process that will ever ring an agent for them or time them out; an age cutoff doesn't fix that, it just marks them "failed" a bit later while they're still stuck on hold.

**Why**: Found via live investigation (VPS logs + a direct Supabase query) — a real caller (`254706651053`) entered the queue, was rung to one agent who didn't answer, and was still sitting in the hold queue three minutes later when an ARI websocket blip forced `ari-app` to restart. The blind reconciliation immediately marked that row `'failed'`, but the caller's actual Asterisk channel was very possibly still alive and on hold at that exact moment — restarting `ari-app` doesn't touch Asterisk, which keeps bridges/channels running on its own. Since the new process's in-memory queue always starts empty, nothing would ever have rung an agent for that caller again or timed them out — they'd have sat on hold indefinitely. This is the direct, confirmed cause behind this week's "call is lost when nobody answers" and "call stuck for 8 minutes" reports. A real `'ongoing'` call surviving a restart was also being wrongly marked `'failed'` on the dashboard immediately, even though the actual conversation was continuing normally in Asterisk.

## 2026-09-04 — Africa's Talking's legacy `/events` webhook reduced to a bare 200 ack

**Decision**: `calls-app/app.js`'s `/events` handler no longer upserts `call_logs`, and no longer looks up/flips a phone-matched agent offline either — it just acks 200, the same "harmless no-op" treatment already given to `/voice`. Deleted `calls-app/lib/agentCache.js` (the in-memory agent-phone cache that existed solely to support this handler's lookup) and its 4 `invalidateAgentCache()` call sites in `api.js`, since nothing reads that cache anymore.

**Alternatives considered**: Keeping the write and instead trying to merge it with the real Asterisk-driven row — not possible without a shared identifier: Africa's Talking's `sessionId` for this webhook is its own `ATVId_...` id, which has no relationship to the Asterisk channel id `ari-app` logs calls under, so the write could only ever create a second, disconnected row for the same real call, never update the real one. Keeping the agent-offline side effect as a safety net — rejected once checking `agents.phone` showed only 2 of 10 agents still have one set (Njogu, and the account owner) from before the SIP-softphone flow; for those 2, this was a live, real bug, not a safety net: a real call whose *destination* happened to equal that agent's phone would force them `offline` even while genuinely active on their SIP line, since ari-app — not this webhook — is what actually owns SIP-based presence now.

**Why**: Confirmed live (2026-09-04) that this webhook is still actively firing for real calls today, despite code comments dating back to the SIP-trunk migration assuming/hoping it had gone quiet ("unverified whether this handler still receives any traffic at all"). It hadn't gone quiet — Africa's Talking fires it independently of which mechanism actually carries the call's audio. Every real call was therefore being logged twice: once correctly by `ari-app`, and once as a confusing, differently-attributed duplicate from this legacy path. The remaining agent-offline logic was reviewed once the duplicate-logging fix went in and found to be worse than useless for the same reason — a leftover from the pre-SIP phone-based agent model that could still misfire against a live SIP call today.

## 2026-09-07 — Asterisk's TURN relay password had drifted out of sync with coturn since it was added

**Decision**: Corrected `turnpassword` in `/etc/asterisk/rtp.conf` on the VPS to the value coturn (`/etc/turnserver.conf`) actually accepts. Confirmed nowhere else in this repo needs the same fix except DigitalOcean's `SOFTPHONE_TURN_PASSWORD` env var (used by `calls-app/api.js` to hand the browser its own ICE/TURN credentials) — flagged to Sam to update via the DO dashboard rather than risk a blind `doctl apps update` spec-replace touching other secrets.

**Alternatives considered**: Changing `/etc/turnserver.conf`'s stored credential to match `rtp.conf` instead — rejected: `turnserver.conf` is the one side I could directly, empirically prove was already correct (a real TURN allocate-and-relay round trip succeeded end to end using its stored value as the password), whereas `rtp.conf`'s value had no such proof behind it. Changing the already-proven-working side to match an unproven one would just move the bug, not fix it.

**Why**: Investigating a reported "answered an incoming call, couldn't hear the caller" complaint. `rtp.conf`'s `turnaddr`/`turnusername`/`turnpassword` block (comment: "added 2026-08-12") is what lets Asterisk itself gather a TURN relay ICE candidate for its side of a WebRTC bridge, needed whenever a plain host/reflexive candidate can't traverse a caller's or agent's network. Config review alone found nothing wrong — WebRTC/ICE/DTLS settings, codecs, transcoding modules, and the firewall's RTP/TURN port ranges all looked correct. Testing the actual credential against coturn directly (`turnutils_uclient`) told a different story: authentication failed immediately with the value in `rtp.conf` ("user chumzagent credentials are incorrect" in coturn's own log), and succeeded completely — full relay allocation, 0% packet loss — using coturn's own stored value instead. So `rtp.conf` had been holding the wrong password since the day TURN was added, meaning every TURN allocation Asterisk itself ever attempted had been silently failing authentication the whole time, forcing ICE down to host/reflexive-only candidates on Asterisk's side. That's consistent with intermittent one-way audio rather than every call — it only bites when an agent's specific network situation actually needs the relay Asterisk didn't have.

## 2026-09-07 — `ari-app` posts to Google Chat on the same events it already logged as `⚠️`/`🧹`

**Decision**: Added a small `alertGChat(text)` helper (`ari-app/index.js`) — POSTs to a `GCHAT_WEBHOOK_URL` env var, fire-and-forget, silently no-ops if that env var isn't set. Wired into exactly four existing call sites that already had a `console.warn`/`console.log` for the event: an agent flipping offline after repeated ring failures, an agent's softphone flapping 3+ times in an hour, `sweepStaleCalls` finding an orphaned call_logs row, `sweepStaleAddPartyRequests` finding an orphaned add-party request, and `reconcileGhostOnCallAgents` finding an agent stuck `on_call` with no live channel. Deliberately did **not** wire it into routine ghost-agent reconciliation (a single stale-tab reconciliation) — the code's own existing reasoning already establishes that as a normal, expected event, and alerting on every occurrence would drown a real incident in noise.

**Alternatives considered**: A generic "forward every `console.error`/`console.warn` call to Chat" approach — rejected as the same mistake in the opposite direction: most of this file's ~50 `console.error` calls are for expected, self-healing, per-call races (a caller hanging up mid-greeting, a lost network round trip already retried) — alerting on all of them would be pure noise from day one, training everyone to ignore the channel. Picking specific, already-decided-to-be-warning-worthy sites keeps the signal meaningful.

**Why**: Every real bug found this week (the stuck-call fix, the TURN-password bug) was only ever discovered by manually going and looking after a symptom was reported — nothing was watching for it as it happened. These five sites are the ones this codebase's own existing comments already treat as genuinely abnormal (not routine self-healing), so they're the highest-confidence "something is actually wrong" signal already sitting in the code, just never sent anywhere anyone was watching.

## 2026-09-07 — Three more proactive checks, plus a credential-duplication audit

**Decision**: Three additions in one pass, each closing a gap the alerting work above still left open:
1. `chumz-healthcheck.sh` now also checks `calls-app`'s own `/healthz` on DigitalOcean (from the VPS, not from inside DO itself — checking a platform from inside itself misses DNS/edge/egress failures a real caller would still hit).
2. `ari-app` gained a `checkNoAgentsDuringBusinessHours` poll (`getLoggedInAgentCount` in `supabase.js`, counts anything not `'offline'` — an agent mid-call isn't a problem, nobody logged in at all during business hours is) — alerts (edge-triggered, same shape as everything else) after 10 minutes of zero, not instantly, to tolerate a normal shift-change gap.
3. Audited every credential referenced in more than one place across the system (`ARI_APP_INTERNAL_SECRET`, `SUPABASE_URL`/`KEY`, `SOFTPHONE_TURN_PASSWORD` — the same shape of bug as the TURN password). Found `ARI_APP_INTERNAL_SECRET` (shared between `ari-app` and `calls-app`, gating every `/internal/*` route) had the exact same silent-failure gap TURN did: a mismatch logged nothing anywhere. Replaced 5 copy-pasted auth-check blocks with one `rejectUnlessAuthorized` helper that logs every rejection and alerts specifically when a secret was *present but wrong* (calls-app always sends one on a real request — a bare scanner probe with no header at all isn't the same signal and doesn't need to page anyone). Verified live against a real request with a deliberately wrong secret: logged correctly, alerted correctly, and a missing-header request logged without alerting.

**Alternatives considered**: Building an automated live round-trip test for `ARI_APP_INTERNAL_SECRET` drift, matching the TURN check's shape (`turnutils_uclient`) — rejected for now: unlike TURN, there's no side-effect-free way to test it (every `/internal/*` route does something real), and unlike TURN's silent partial-degradation, a real mismatch here breaks the claim/hold-music features outright and immediately, with a visible dashboard error — lower risk of quietly going unnoticed for weeks. The new rejection logging/alerting is the proportionate fix; a live test can be revisited if this ever actually drifts. `SUPABASE_URL`/`KEY` duplication also flagged but left unaddressed the same way — a mismatch there fails loudly (every DB call breaks at once), not subtly.

**Why**: Asked "what else can we do" after wiring up the first alerts — the honest answer was that `calls-app` itself still had zero monitoring, "nobody logged in" is a real failure mode this week's own incidents traced back to (distinct from any technical fault `/healthz` could ever catch), and the TURN bug's actual root cause — a credential silently duplicated across systems with nothing checking they still agree — was worth checking for elsewhere before assuming it was a one-off.

## 2026-09-07 — Dependency-vulnerability audit: one real fix, several genuinely not safe to force

**Decision**: Committed `ari-app/package-lock.json` (previously missing from this repo entirely — fetched from the VPS, where it already existed) and applied `web`'s `fast-uri`/`nanoid` fixes (both non-breaking, verified `npm run build` still succeeds). Deliberately did **not** touch anything else `npm audit` flagged, after actually checking what each "fix" would really do:
- `ari-app`: every version of `ari-client` up to and including the latest (`2.2.0`) depends on the long-abandoned `request` package (2 critical + several moderate CVEs, mostly in `form-data`). `npm audit fix --force`'s suggested "fix" is to install `ari-client@1.2.0` — a **downgrade**, not an upgrade (nothing newer exists), losing two major versions of whatever changed since. Left alone; a real fix here means either an `overrides`-based surgical patch of just the leaf packages (`form-data`/`qs`/`tough-cookie`/`uuid`) while keeping `ari-client@2.2.0` itself, or accepting the risk given ari-client's actual usage here (local JSON REST calls to Asterisk over localhost, never handling attacker-controlled multipart uploads or cookie jars) doesn't obviously touch the vulnerable code paths.
- `calls-app`: `qs` (via `body-parser`) and `uuid` (via `gaxios`) both need a real major-version jump outside this project's own declared ranges — `body-parser` fixed `qs` only in `2.x` (`express` itself would need to go to `5.x` first), and `gaxios`'s fix only ships from `google-auth-library@10+` (currently pinned `^9.0.0`). Neither is a same-day safe fix.
- `web`: `react-router` 6→7 is a real breaking migration (confirmed: currently on `6.30.6`, fix wants `7.18.3`), not attempted here. `esbuild`/`vite` and `sharp`/`vite-plugin-pwa` are dev/build-tooling only — they run on a trusted machine during `npm run build`, never in a real user's browser or on the production server — lower real-world risk, left for a deliberate `vite` major-version upgrade later rather than forced today.

**Alternatives considered**: Running `npm audit fix --force` everywhere to just clear the count — rejected outright once the actual diffs were checked; several of these "fixes" are downgrades or major-version jumps that could silently break the exact call-routing/auth code this whole week was spent hardening, for a security benefit that in at least `ari-client`'s case isn't clearly real given how it's actually used here.

**Why**: Came out of the broader "other areas of failure" review — `npm audit`'s summary numbers looked like quick wins until each one was actually traced through; most weren't. Recording this so a future "just run audit fix" pass doesn't rediscover the same dead ends, and so the real remaining work (an `ari-client` overrides patch or careful major bump, `express`/`google-auth-library` majors, the `react-router` v7 migration) is written down as its own deliberate task instead of looking done.

## 2026-09-07 — `ari-app`'s `ari-client`/`request` vulnerabilities: left alone, deliberately

**Decision**: `ari-client` stays at `2.2.0` (latest). Its 9 reported vulnerabilities (2 critical, in `form-data`, plus `qs`/`tough-cookie`/`uuid` — all transitively via the long-abandoned `request` package) are not being patched.

**Alternatives considered**: `npm audit fix --force` — actually a *downgrade* to `ari-client@1.2.0` (no newer version exists; nothing has ever dropped `request`), losing two major versions of whatever changed since, for a fix that doesn't obviously address a reachable vulnerability (see below) — rejected. Forcing just the leaf packages via `package.json` `overrides` while keeping `ari-client@2.2.0` — investigated and rejected specifically for `uuid`: `request`'s own `auth.js`/`multipart.js`/`oauth.js` do `require('uuid/v4')`, an import path modern `uuid` (≥7) removed entirely, so forcing it would risk a hard `Cannot find module` crash in the core telephony library the instant any code path touched those files.

**Why**: Checked whether the vulnerable code is actually reachable before deciding to leave it: `form-data`'s critical CVEs and `request`'s `uuid` usage only trigger through `request`'s multipart-upload and OAuth submodules. Confirmed via `grep`, in both `ari-app/index.js` and `ari-client`'s own lib code, zero use of `formData`/multipart/OAuth anywhere — every call this app makes to Asterisk's ARI is a plain JSON REST body over localhost. The vulnerable code paths exist in the dependency tree but are never executed by this app. Revisit if `ari-client` ever ships a version that's dropped `request`, or if this app ever starts using ARI's recording/media-upload features (which might route through `request`'s multipart path).

## 2026-09-07 — Production-readiness pass: security headers, and removed the last flagged firewall rule

**Decision**: Added `helmet` to `calls-app` with an explicit (not default) CSP, and removed `ufw`'s long-flagged unused `5061/tcp` rule from both the live VPS and the tracked `infra/` mirror.

**Alternatives considered**: helmet's default CSP (`connectSrc` limited to `'self'`) — would have silently broken the browser softphone, which opens a WebSocket straight to `sip.chumz.online` (a different origin) for SIP signaling; caught by actually checking `web/src/lib/softphone.tsx`'s real connection targets before writing the policy, not by trusting the library's defaults. Leaving CSP off entirely and shipping only the other headers — rejected as half a fix; CSP is the one helmet header that actually mitigates XSS, which was the point of adding this at all.

**Why**: Came out of the production-readiness audit (Google Chat readiness board, 2026-09-07) — "no security headers" and "a stale firewall rule with nothing listening" were both flagged there. Confirmed live via `ss -tlnp` (again) that nothing binds `5061/tcp` before removing it — a leftover from a removed/never-implemented SIP-TLS transport, per the same finding recorded back on 2026-08-31.

Two more readiness-board items closed out the same day: Sam tested a real outgoing and a real incoming call after the CSP shipped — softphone unaffected, confirming the `connectSrc`/`styleSrc` exceptions above were the right ones. The caller-privacy/Kenya DPA 2019 review was deliberately skipped (Sam's call, not a technical finding) — still worth reopening before this system handles meaningfully more call volume or a different customer base.

## 2026-09-07 — Confirmed: Supabase is on the free tier, with no backups at all

**Decision**: No code change yet — recording the finding. Sam confirmed directly in the Supabase dashboard: free tier, no automated backups and no point-in-time recovery configured (Supabase doesn't offer either on the free tier at all — daily backups start at Pro, PITR is a paid add-on above that).

**Why this matters**: every real customer record this system has — `call_logs`, `agents`, `tickets`, IVR config, business hours — exists in exactly one place, with no way to recover any of it if the project were ever lost, corrupted, or hit by a bad migration or an accidental delete. This is the most severe unmitigated finding from the whole production-readiness pass — worse than anything fixed this week, because none of this week's fixes touch it at all. Needs a real decision (upgrade the Supabase plan, or stand up an independent scheduled export as a stopgap) — not a code change made unilaterally, since it has a real cost either way.

## 2026-09-07 — `ari-app` rollback is now a script, not a remembered manual sequence

**Decision**: Added `infra/systemd/chumz-ari-rollback.sh`. Restores `index.js`/`supabase.js`/`package.json`/`package-lock.json`/`.env` from the timestamped backups every deploy this week has already been leaving in `/opt/chumz-ari-app/backups/` — no-arg restores each file to its own most recent backup (undoes whatever the last deploy touched); a timestamp argument targets an exact point; `list` shows what's available. Same safety discipline as every other change to this box: confirms zero active calls immediately before restarting (not just at the start), backs up whatever it's about to overwrite first (so a rollback is itself always reversible), and refuses to restart the service if a restored `.js` file fails `node --check`.

**Why**: The production-readiness plan flagged this as a real gap — restoring a backup meant remembering which timestamped file matched which deploy and `scp`-ing it back by hand, exactly the kind of manual step that's fine when calm and risky under real pressure. Verified safely: `list` mode against the real backup directory, and a full dry run of the default restore path (declined at the confirmation prompt) correctly identified the right backup for each file with zero side effects.

## 2026-09-07 — A first real test suite for `calls-app` and `ari-app` (skipping staging for now)

**Decision**: Added `vitest` (+ `supertest` for `calls-app`) to both apps, each with `npm test`. `calls-app`: 25 tests across `lib/phone.js` (E.164 validation/normalization), `auth.js`'s `requireAuth`/`requireSupervisor` (valid/invalid/expired sessions, the sliding-session refresh re-checking a demoted role against the roster, the supervisor-only 403 paths), and a `supertest`-driven integration check that `/api/queue` is actually gated by `requireAuth` and correctly separates "still in the IVR menu" from "on hold" callers. `ari-app`: extracted `errText`/`safeEqual`/`isWithinBusinessHours`/`parseSipUsername` out of `index.js` into a new `lib/helpers.js` — they were pure functions with no Asterisk/network dependency, but private to a 2000-line file that itself connects to a live ARI socket at require time, so there was no way to test them in isolation without moving them first. 15 tests now cover all four, including the business-hours boundary conditions (open-at-08:00, closed-at-exactly-17:00, closed-on-Saturday) that would otherwise only ever surface at exactly the wrong hour of the day.

**Alternatives considered**: Testing `ari-app`'s call-routing/bridging logic directly (queue, dequeue, bridge, hangup) — deferred. That logic is deeply entangled with a live `ari-client` WebSocket/REST connection; mocking it faithfully enough to be trustworthy (not just green) is a real project of its own, not a same-day addition, and is exactly the kind of thing a staging environment (explicitly skipped for now, Sam's call) would make dramatically more tractable to do for real.

**Why**: Every fix this week was verified by hand against live production because there was nothing else to verify it against — the readiness audit's own "Testing" category was the weakest on the whole board (0 passing checks out of 7). This doesn't close that gap, but it's a real, working start: the extraction pattern used for `ari-app` (pull pure logic out of the monolith into something requirable in isolation) is also the template for testing more of it later, incrementally, the same way.

Correction to the readiness board's own earlier finding: a re-check found `web` was never actually at zero tests — the original search used a `*.test.tsx` glob that missed plain `.test.ts` files, and `web/src/lib/{api,phoneFormat}.test.ts` (13 passing tests) had existed the whole time. Fixed on the published board.

## 2026-09-07 — CI now runs all three test suites, but does not yet block `calls-app`'s deploy

**Decision**: Added `.github/workflows/ci.yml` — one job per app, each `npm ci`+`npm test`; `web`'s job also runs `lint` and the real production `build` (`tsc -b`, catching type errors the dev server tolerates). Runs on every push and PR against `main`.

**Alternatives considered**: Making this a true deploy gate — turn off `deploy_on_push` in `calls-app`'s DigitalOcean App Spec, add DigitalOcean's own GitHub Action as a final step here, gated behind the test jobs passing. Not done today: it needs a `DIGITALOCEAN_ACCESS_TOKEN` with deploy permission added as a GitHub Actions secret, and this session's own `doctl` token was already confirmed (much earlier this week) to lack that exact permission — someone with DO dashboard + this repo's GitHub settings access needs to generate a new scoped token and add it as a secret before this upgrade is possible.

**Why**: Closes the last open item from the "make changes safe to make" phase of the production-readiness plan, but honestly, not completely — right now this workflow and DigitalOcean's own auto-deploy both fire off the same push webhook and run in parallel, so a red X here is visible feedback, not a stopped deploy. Worth being upfront about that gap rather than letting "CI is wired up" sound like more protection than it actually is yet.

## 2026-09-08 — `infra/bootstrap.sh`, and three real gaps it surfaced along the way

**Decision**: Added `infra/bootstrap.sh` — provisions a fresh Ubuntu 24.04 droplet into a working copy of `sip.chumz.online`, written by reading every package's exact installed version directly off the live box rather than from memory. Writing it surfaced three things the existing `infra/` mirror had never actually covered, now fixed:
- `/etc/fail2ban/jail.local` and its custom `asterisk-tls-scan` filter (`/etc/fail2ban/filter.d/asterisk-tls-scan.conf`) — the *actual* jail enablement (ports, logpaths, the custom TLS-scan protection added earlier this project) was completely untracked; only the stock Debian default (`sshd` only) would have survived a rebuild.
- `/etc/asterisk/logger.conf` — a real customization (routes to `messages.log`/`security`, not Asterisk's stock default), and the fail2ban jails above depend on exactly those two files existing.
- `/etc/asterisk/pjsip.conf`'s structural, credential-free sections (the transports and the Africa's Talking trunk) had no template anywhere — the file was entirely excluded for its per-agent passwords, but that meant even the parts with zero credentials in them were undocumented too. Added `asterisk/pjsip.conf.template` with just those sections; real agent blocks still come back through `ari-app/pjsipConfig.js`'s normal provisioning, not a file.

**Alternatives considered**: Jumping straight to Terraform/Ansible, per the original phrasing of this plan item — rejected for now, per the plan's own reasoning: a rebuild had never been rehearsed even once, and it turned out `infra/` genuinely wasn't sufficient yet (see above) — real IaC tooling on top of an unverified foundation would just formalize the same gaps. This script is the honest prerequisite; revisit real IaC once it's actually been used.

**Why**: This was the first of the three "Later"-phase production-plan items (load testing, redundancy, infra-as-code) — chosen first specifically because writing it required actually checking whether `infra/`'s existing mirror would work for a real rebuild, rather than assuming it from how thorough it looked. It didn't, in three concrete, fixable ways.

## 2026-09-15 — Ring-all redesign: cancel siblings on answer, not Stasis-entry; CAS for agent-status writes

**Decision**: `bridgeAgentLeg` previously claimed a customer session and hung up every sibling ring (`stopSiblingRings`) the instant a leg entered Asterisk's Stasis app — which happens at channel-creation time, essentially simultaneously for every agent in a ring-all fan-out, well before any of them has actually been answered. So "first to answer wins" didn't actually hold: whichever leg's `StasisStart` the event loop happened to process first won, regardless of who picked up. Moved the claim to after `agentChannel.answer()` actually succeeds, with a last-surviving-leg count (via the existing `ringGroupBySessionId` array) so a customer whose siblings fail at different times gets requeued exactly once, never zero or twice.

Generalized `setAgentStatus` (ari-app/supabase.js) to take an optional `expectedStatus`, turning it into a compare-and-swap — the same atomic `UPDATE ... WHERE ...` idiom `claimAddPartyRequests` already used elsewhere in this file. Applied to `ringOneAgent`'s claim (closing a race where two concurrent claims for the same agent — a `dequeueNext` tick racing a `claimQueuedCall`, or two overlapping `dequeueNext` ticks — could both originate a real leg to the same softphone) and to every ring-phase revert-to-`available`, so an agent's own explicit status change mid-ring (e.g. clicking "Take a break" while their phone is still ringing) can't be silently clobbered back by cleanup.

Added `POST /internal/agent-live-status` (ari-app) and `checkAgentLiveOnAsterisk` (calls-app) so a status write from the dashboard can check whether ari-app genuinely has that agent ringing/bridged before writing `agents.status` — self-service status changes (`PATCH /api/agents/me/status`) are blocked outright while live; a supervisor's roster edit (`PATCH /api/agents/:id`) is still allowed (an intentional escape hatch for a stuck/ghost record) but now returns a warning.

**Alternatives considered**: CAS'ing `bridgeAgentLeg`'s `teardown()` and `finishOutboundCall`'s final `available` reverts against `'on_call'` too, matching every other cleanup path — this was the original plan, but building it surfaced a real regression risk: both can fire while an agent's true status is still `'ringing'` (a hangup racing the bridge-formation window, before the `on_call` write has landed), and CAS'ing against a single expected value there could leave an agent permanently stuck at `'ringing'` forever. Left those two reverts unconditional instead — they only ever fire once a call has *definitively* ended, where reverting to `available` is the correct terminal state regardless of what the row said a moment before.

For the reverse race (a stale `agents.status` write clobbering a genuinely live call), considered having a supervisor's status override also hang up the real call via ari-app's existing `/internal/hangup-call`, to keep the DB and reality perfectly in sync — rejected as a bigger behavior change than this fix should carry (a status edit starting to end real customer calls) without an explicit product decision; Sam chose warn-but-allow instead.

**Why**: This is the most consequential fix in the whole pass — it directly affects which agent actually gets a real customer call today, not just bookkeeping accuracy. Verified against an upgraded version of the existing `queue-simulation.js` load-test harness (previously `answer()` never failed, so none of this logic was ever actually exercised): clean runs across the original 30:4/3:10/5:5/200:15 customer:agent ratios plus new high-failure-rate runs (60% induced answer failures against 3 agents, 20-agent ring groups at 50% failure), and a dedicated scenario forcing a `claimQueuedCall`/`dequeueNext` race for the same agent. Still needs a short manual/staging check against a real Supabase instance before the CAS itself (a JS harness can prove the orchestration logic is correct *given* atomicity, not the atomicity guarantee itself) and the redesign are both fully deployed — and migrations 024/025 must be run before this ari-app build ships.

## 2026-09-22 — Finance wallet: track and reduce Chumz's own call-cost balance, billed per second

**Decision**: Added a wallet module tracking Chumz's own prepaid call-cost balance — one global wallet (not per-agent/per-client, confirmed with Sam), billed per second at call-end from the exact `duration` value `ari-app` already computes and writes to `call_logs`, not a live ticker. Researched wallet/ledger best practices first (Stripe's internal ledger model, Postgres concurrency patterns, metered-billing norms) before designing.

Schema (migration `026_finance_wallet.sql`): a singleton `wallet` row (`balance_cents`, `rate_micros_per_second`, `low_balance_threshold_cents` — matches the existing `ivr_config` singleton convention) plus an append-only `wallet_transactions` ledger, both only ever mutated through one Postgres function, `wallet_apply_transaction` — idempotent via a unique `reference` per transaction (`call:<session_id>` for usage, a UUID for top-ups), atomic via a single `UPDATE ... RETURNING`. Called via `supabase.rpc(...)` from both `ari-app` (usage debits, new `ari-app/wallet.js`, hooked into the two existing call-end sites in `index.js`) and `calls-app` (manual top-ups/config, new `/api/wallet*` routes) — the atomicity/idempotency logic lives once, in the database, not duplicated in two Node codebases. New supervisor-only `web/src/pages/Wallet.tsx` for balance/top-up/config/history.

Deliberately scoped out, and said so explicitly rather than building them in quietly:
- **No call-blocking on low/zero balance.** Billing is settle-at-end — the call already happened by the time it's charged, so a debit is never rejected for insufficient funds (it would just make the ledger wrong). Blocking *new* calls when the balance is low is a real, separate product decision (Chumz's own inbound calls could get refused) that wasn't asked for; this only alerts (reusing the existing `alertGChat`) on crossing the configured threshold, edge-triggered so it fires once per crossing, not once per debit while still low.
- **No payment gateway/M-Pesa integration.** Top-up is a supervisor manually recording "I already paid Africa's Talking X" — the idempotency-by-reference design already anticipates pointing this at a real webhook later (its delivery id would just become the `reference`), but nothing here assumes that's coming.
- **No reversal endpoint**, though the ledger's `type` check constraint already includes `'reversal'` so a future correction never needs a migration — no reversal flow has been asked for yet.

**Why**: per-second billing settled at call-end (rather than a live poller) matches how Africa's Talking/Twilio actually bill, and this codebase already computes exactly the right duration once per call (`teardown()`'s and the outbound hangup handler's existing `duration` calculation) — reusing that value beat building new call-lifecycle tracking. Integer minor units + one rounding per finished call (not per tick) sidesteps the float-drift failure mode that specifically afflicts live-ticking metered billing.

**Deployed 2026-09-22**: migration 026 applied to production Supabase, `ari-app` deployed to the VPS (backed up first, zero active calls confirmed, `/healthz` and `chumz-healthcheck.sh` clean afterward), `calls-app`/`web` pushed to `main` for DO's auto-deploy.

**Bug found and fixed during deploy verification**: the first real `wallet_apply_transaction` call failed with `column reference "balance_cents" is ambiguous`. Root cause: the function's `RETURNS TABLE` output column is named `balance_cents` — same as the real column on `wallet` — and Postgres's default `plpgsql.variable_conflict = error` refuses to guess which one `set balance_cents = balance_cents + p_amount_cents ... returning balance_cents` means, rather than silently picking one. Fixed with a `#variable_conflict use_column` pragma at the top of the function body (the standard, documented fix for this exact, well-known plpgsql gotcha) instead of renaming the output column, which would have meant updating every call site instead of one line in the function. Verified live afterward: a real top-up applied and moved the balance correctly, an immediate duplicate-reference call correctly no-op'd (`applied: false`, balance unchanged) proving the idempotency guard itself works, and the low-balance edge-detection correctly fired on a reversal that crossed the (default, 0) threshold. The test top-up was reversed rather than deleted, consistent with this ledger's own "never mutate history" design — production's `wallet_transactions` now has one real, harmless top-up/reversal pair from this verification, net zero balance.

Caught only because deploy verification actually ran a real RPC call rather than trusting `tsc`/lint/unit tests alone — none of those exercise real Postgres function bodies.

## 2026-09-22 — Split wallet billing rate by call direction (inbound vs outbound)

**Decision**: The wallet previously billed every call — inbound and outbound — at one shared rate. Split into `inbound_rate_micros_per_second`/`outbound_rate_micros_per_second` on `wallet` (migration 027), plus a `direction` column on `wallet_transactions` (nullable, only set on `'usage'` rows — kept as its own column rather than folded into `type`, e.g. `'usage_inbound'`, since direction is an orthogonal tag, not a different kind of ledger operation, and a separate column keeps a future "spend by direction" report a plain `where`/`group by`). `wallet_apply_transaction` gained a `p_direction` parameter, same idempotency/atomicity logic otherwise unchanged. `ari-app`'s two existing call-end sites (inbound `teardown()`, the outbound hangup handler) already know their own direction structurally — each now just passes its own hardcoded `'inbound'`/`'outbound'` literal into `applyCallUsageCharge`, no new detection logic anywhere.

**Why**: researched Africa's Talking's actual published Kenya voice rates before assuming this was worth doing — inbound and outbound are genuinely priced roughly 4.5x apart (~KES 1.00/min inbound vs ~KES 4.50/min outbound), so a single shared rate was never actually going to be correct for both directions. Landed before the rate was ever set to a real nonzero value in production, so nothing was mis-billed by the old single-rate design.

**Accepted transition gap**: between running the migration and redeploying `ari-app`, the still-running old process calls the now-removed `rate_micros_per_second` column and gets an error — `getWalletRate`'s existing error handling logs it and returns 0 rather than throwing, so any call ending in that window simply isn't billed, not a crash. Deployed the redeploy immediately after the migration to keep this window as short as possible.

**Bug found in production**: Sam reported top-up failing with "Failed to record top-up" right after this shipped. `create or replace function` only replaces a function with the *exact same parameter list* — adding `p_direction` gave `wallet_apply_transaction` a different signature, so Postgres created a **second overload** (5-param and 6-param versions both existing) instead of replacing the original. `ari-app`'s wrapper always happens to pass all 6 named parameters, so it never hit this; `calls-app`'s top-up route only ever passed 5 (no direction to give), which matched both overloads and PostgREST refused to guess (`PGRST203`, "Could not choose the best candidate function"). Root-caused from `doctl apps logs` (DO's runtime logs — not initially available in this session; became reachable once re-checked). Fixed by explicitly `drop function if exists wallet_apply_transaction(text, bigint, text, text, text)` before the `create or replace`, added to migration 027 itself so a fresh rebuild never recreates the ambiguity. Also hardened `calls-app`'s top-up call to always pass every current parameter explicitly (including `p_direction: null`) rather than relying on defaults for the ones it doesn't need — a partial parameter list is exactly what let this ambiguity bite in the first place, and it would bite the same way again the next time a migration adds another optional parameter unless every call site stays explicit. Verified live: the exact 5-parameter call shape that previously failed now succeeds cleanly; reversed the test transaction afterward, balance back to 0.

**What happened**: Sam reported agent 1 (Samuel) got flipped to `offline` while actually on a call, earlier the same day.

## 2026-09-24 — Load-test coverage for the internal-call CAS fix

**Decision**: Sam asked to add the load-test scenario flagged as missing above — the internal-call double-booking fix (item 1 in the previous entry) had only been verified by manual tracing, unlike the original ring-all CAS, which `loadtest/queue-simulation.js`'s `testClaimRace` already exercises. Added `testInternalCallRace`, same shape: races `handleInternalAgentCall` against `tryDequeueNext` for one contested target agent, asserts at most 1 real origination lands (both mechanisms dial the identical `PJSIP/<username>` endpoint string, so a double-booking always shows up as >1 regardless of which side wins), then verifies the target agent's status is correctly reverted to `available` afterward — the specific thing the old code got wrong (it only ever reverted a bridged internal call, never a merely-ringing one).

Required extending the harness itself, not just adding a scenario: exported `handleInternalAgentCall`, `finishOutboundCall`, and `outboundBySessionId` from `index.js` (test-only, same pattern as the existing exports — never imported by production code); added `getAgentBySipUsername` to the fake Supabase mock (needed for the outbound/internal call-log attribution path, which none of the existing ring-all scenarios touch) and no-op `ring()`/`ringStop()` to `FakeChannel` (called unconditionally by `handleOutboundAgentCall` on the caller's own channel).

**A real design bug found and fixed while building the scenario, before it ever shipped**: the first draft assumed `dequeueNext`'s ring-all attempt would always target this scenario's own test customer. It doesn't — `dequeueNext` always dequeues from the *front* of the shared `waitingQueue`, and by the time this scenario runs (after the main round loop's own customers have settled), that queue can still hold real, unbridged leftover customers from the main loop. Caught this by deliberately swapping the race's `Promise.all` order to force the ring-all-wins branch (never naturally exercised otherwise, since `handleInternalAgentCall` deterministically wins the un-swapped order) — running it immediately surfaced a stale `ringGroupBySessionId` entry and a "customer lost" assertion failure, because the scenario had silently stolen and stranded an unrelated main-loop customer instead of contesting its own. Fixed by setting the shared queue aside for the scenario's duration (`waitingQueue.splice(0, waitingQueue.length)`) and restoring it afterward, guaranteeing `dequeueNext` can only ever contend for the one customer this scenario controls, regardless of who wins. `testClaimRace` above doesn't need this — its own winning path (`claimQueuedCall`) never touches `waitingQueue` at all.

**Verified the test actually catches the regression it's named for**, not just that it passes: temporarily reverted the CAS claim in `handleInternalAgentCall` back to a plain status read and re-ran the harness — it correctly failed with "2 legs originated to the same target agent — should be at most 1". Restored the real fix, confirmed clean again, then ran the harness under several parameter combinations (default, a small 5-customer/2-agent pool, `answerFailureRate=0.4`, and more agents than customers) to check the queue-isolation fix holds generally, not just for the default run. `ari-app`'s 20/20 unit tests still pass; `node --check` clean on both changed files.

Not deployed — this is test-only code (the harness and index.js's test-only export list), nothing that runs in production.
